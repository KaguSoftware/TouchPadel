# Multi-venue, slices 3–4 and "Open a new branch" (2026-09-26)

This note covers the rest of Phase 2's milestone 1, after slice 1 (`slice-1-2026-09-21.md`,
0122–0139) and slice 2 (`slice-2-2026-09-26.md`, 0207–0214).
- **Slice 3** (0215–0221): writes, the day and every guard work per branch.
- **Slice 4** (0222–0227): stations, branch status, realtime, guest reads, staff read scope, and the
  operator, mobile and web apps. It also delivers the owner's **"Open a new branch"** (MV1).

The plan was approved by Parsa on 2026-09-26, with decisions MV1–MV8 (see `slice-2`). This note
also records two decisions taken while building, MV9 and MV10, which change how the apps name
their branch.

## Decisions taken while building

| # | Question | Call |
|---|---|---|
| MV9 | How the server learns which branch an operator request is for. The plan said to re-issue ~45 RPCs to `set_config('app.station_id', p_device_id)`. | The operator sends **`x-station-id`** (this machine's station) and **`x-venue-scope`** (the rail switcher's branch, or `all` on report pages) on every request. PostgREST exposes both as `request.headers`. `app.resolve_venue` reads them as steps 2b and 2c, after anything the server itself asserted. Each is counted only for the owner or a member of that branch. They are exactly as client-asserted as `p_device_id` already was. They also reach column defaults and bodies that never took `p_device_id`, with no RPC re-issued. `replay` forwards the queued write's station. Proven locally: the header reaches `current_setting('request.headers')`, and the CORS preflight allows both headers. |
| MV10 | Owner and two-branch staff screens mixing branches. RLS gave every staff read `staff_venue_ids()`, meaning every branch the reader works at. | `app.visible_venue_ids()` (0226) is the branch in scope: the owner's header branch (`all` = every branch), else the station's branch, else the reader's only or all branches. It is always a subset of `staff_venue_ids()`. All 69 staff read policies were regenerated from their live definitions to use `(select app.visible_venue_ids())`, evaluated once per statement. `venue_settings_staff_read`, which had no venue axis, follows it too. The guest branch of the catalogue policies no longer applies to staff. **Screens need no per-query branch filter**: a switch resets the query cache and everything reloads for the new branch. |
| — | The owner's "All branches" | Only the report and analytics pages offer it (`ReportBranchScope`), and only while they are open. The rail switcher always picks one branch, so a till or desk never shows two branches. Clock-and-hours figures (occupancy, business days) use one branch's clock (`app.analysis_venue()`); the page says so. |
| — | Who may switch branches | The owner, or a manager at two branches, on a machine that is **not a registered station**. A registered till trades for its own branch only. |
| — | Promotions per branch | See MV2 in slice 2. `set_promotion_venue` is the chain-wide switch. |
| — | Photos of a copied branch | Shared (MV6). `app.storage_path_in_use(path)` is true while any row still points at the object, and the operator's `removeMedia` keeps it in that case. |

## Apps

**Operator:**
- `lib/venueScope.ts`: the headers and a `venueFetch` wired into the Supabase client.
- `lib/venue.tsx`: `VenueProvider`, `useVenue`, `pickBranch` and `branchTopic`.
  - `useBroadcast` picks the per-branch topic.
  - The rail shows the branch, or a switcher (`components/RailBranch.tsx`).
- **Setup › Branches** (`/admin/branches`, owner): the list, "Open a new branch", the readiness
  checklist with "Fix" links, "Open to guests", "Close branch" and "Print table QR codes".
- **Settings › Venue details › Stations:** register this machine at the branch, and retire a station.
- **Staff:** a new account works at the branch in scope, and the record has a Branches section
  (owner).
- **Reports and analytics:** a "This branch / All branches" toggle (owner).
- `removeMedia` keeps a shared photo.
- Strings live in `ws.branches.*` (EN + AR).

**Mobile** (built by a helper agent, reviewed):
- A branch picker on the Book tab and on Availability. It is hidden with one branch and remembered
  in `tp.venue`.
- Availability, settings, degraded mode and realtime (`courts:<venue>`) are per branch.
- Booking history and booking detail use each booking's own branch.
- The staff floor listens on `floor:<venue>`.

**Web** (helper agent, reviewed):
- The menu, cafe settings and venue mode follow the table's branch. The first paint uses
  `table_branch`, and binding uses `open_table_session.venue_id`.
- A walk-in with several branches gets a chooser (`?b=<slug>`).
- The club site's Visit block, footer and JSON-LD list every open branch from `venues`, falling
  back to today's hard-coded address.

## Rollout (every push to `main` applies migrations to production at once)

1. **Owner, first:**
   - Confirm hosted is at 0206 (`npx supabase migration list --linked` from `packages/db`).
   - Create the staging project and rehearse 0207–0227 there.
   - PITR stays the owner's decision.
2. Push the migrations with the waiver text:
   `MIGRATION-RISK-ACCEPTED: multi-venue slices 2-4 — unique indexes on 1-row venue_settings and
   ~25-row cafe_settings; SET NOT NULL backed by validated CHECKs; slice-3 venue indexes on
   one-branch tables`.
   - With one venue nothing changes for users: every default resolves as before, and the legacy
     realtime topics still broadcast.
   - `functions-deploy.yml` redeploys `replay`, `staff-admin`, the Telegram functions and the
     assistant functions in the same push.
3. Cut the operator tag and install it on **every station**, so they send the headers and
   subscribe to the per-branch topics.
4. The web deploys itself (Vercel). The mobile changes ride in the 1.0 store build (owner-run
   `eas build`).
5. Only then: **Setup › Branches › Open a new branch**. Then:
   - give it a manager (the staff record's Branches);
   - register its tills (Settings › Venue details › Stations);
   - check hours, rates and the menu;
   - print the table QR codes;
   - receive opening stock;
   - press **Open to guests**.
6. A later migration stops the legacy `kds` / `floor` / `courts` broadcasts and drops the
   deprecated `venue_settings.llm_*` columns, once every station runs the new operator.

## Known limits and follow-ups

- **The owner assistant** runs its tools as the owner's JWT with no scope header. With two open
  branches it therefore reads every branch. A per-conversation branch scope (plan item) is not
  built yet.
- **Consolidated clock:** "All branches" reports use one branch's clock and business day for
  hour-based figures. The UI names the branch.
- **e2e:** `helpers.ts` (`ensureTillFresh`, `.single()` settings reads) still assumes one venue.
  That is fine while CI has one; a two-branch e2e spec is still to write.
- **Web fallback:** if the branch list cannot be read, the menu falls back to the unfiltered read.
  With two open branches that mixes both menus; it is an error path only.
- **Mobile first launch:** with an empty cache, the grid waits one extra round trip for the branch
  list.
- **Local-only test noise** (not from this work):
  - `protocol-action` served-function cases need `supabase functions serve`.
  - A long-lived local database collects test courts until the 400-day courts summary times out.
  - Leftover heartbeats and PIN attempts affect some probes. Clear `app.pin_attempts` and stale
    `device_heartbeats`.
