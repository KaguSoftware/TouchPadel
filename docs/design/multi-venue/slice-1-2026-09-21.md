# Multi-venue, slice 1 — the schema foundation (2026-09-21)

Milestone 1 of Phase 2 (`PHASE-2-PLAN.md`, C0) is multi-venue: a real second branch with shared
guests, one owner over all branches, managers per branch. Nothing in migrations 0001–0121 carried
a venue: `venue_settings` was a boolean-PK singleton, `staff.role` was venue-less, and every RPC,
policy, cron job and realtime topic assumed one building. This note records what slice 1 changed
(migrations **0122–0138**), the calls behind the shape, and what the later slices inherit. The
decision record for the programme stays `PHASE-2-PLAN.md`; the live tick list is
`PHASE-2-CHECKLIST.md`.

## The four slices

| Slice | Contents | Production visible? |
|---|---|---|
| **1 (this)** | `venues`, `venue_id` on 35 scoped tables with a backfill, `staff_venues`, a `stations` registry, the resolver helpers, the RLS venue axis, composite uniques, a two-venue fixture and the gates | No. One venue, every default resolves, zero app changes |
| 2 | `platform_settings` split off `venue_settings`; one `venue_settings` row per venue; the 35 functions that read `venue_settings` re-issued; `cafe_settings` per venue; `SET NOT NULL` on `venue_id` | No |
| 3 | RPC families re-issued with `set_config('app.station_id', p_device_id, true)` and explicit cross-venue guards; `open_day` / `business_date` per venue; the `(venue_id, …)` index set; `VENUE_MISMATCH` | No |
| 4 | Owner venue switcher, mobile venue picker, web default venue, station registration screen, per-venue realtime topics, the assistant's venue axis, the owner RPC that creates a venue | Yes — the second branch opens |

A second **active** venue must not exist on the client's project before slice 3: a guest
`hold_slot` or `open_table_session` insert then has no way to name its venue and is refused with
`VENUE_REQUIRED` (by design — never silently filed at the wrong branch).

## Decisions

| # | Question | Call |
|---|---|---|
| R1 | Column default | `default app.current_venue()` on tables written only by identified callers; `default app.current_venue_or_default()` on the eight tables also written by cron or `service_role` with no caller (`audit_log`, `degraded_periods`, `manager_alerts`, `telegram_outbox`, `telegram_actions`, `analytics_insights`, `analytics_patterns`, `analytics_insight_rejections`). Never `default_venue()` on a business table: a row is filed where the caller belongs, or the write is refused loudly. |
| R2 | When `heartbeat` refuses a station | It auto-registers at `app.resolve_venue()` when the caller's venue is unambiguous and raises `STATION_UNKNOWN` only when it is not (an owner with no station and two venues; a staffer at two venues). The literal rule "refuse once two venues exist" would have broken every till at venue A the day venue B was created. |
| R3 | Zero-argument `is_degraded()` / `venue_mode()` | Delegate through `current_venue_or_default()`. Both are granted to `anon` and run on the guest menu before any identity; they must never raise. |
| R4 | Membership for seeded and future staff | A trigger on `staff` (insert, and update of `role`) gives every non-owner a `staff_venues` row at the default venue. Migrations run before `seed.sql`, so a one-off backfill alone would have left every dev staffer with no membership and every venue-axis policy hiding everything. The trigger also covers `app.register_staff`. |
| R5 | NOT NULL | A validated `CHECK (venue_id is not null)` only. `check-migrations.mjs` blocks `set not null` with no exemption; the CHECK is the same guarantee, and `types.gen.ts` keeps `venue_id: string \| null` so no client type moves in slice 1. |
| R6 | Venue B in tests | `fixtures/venue-b.sql` behind `db:fixtures:venue-b`, never in the default list (it would renumber the e2e desk grid, break a `table_number` `.single()` read and move the bench court count). The db suite builds its own probe venue B in `tests/multi-venue.test.ts` and **deactivates** it in `afterAll` — deletion is impossible once append-only rows reference it. |
| R7 | `PRINCIPALS` in the RLS matrix | Stays at 8. A ninth principal is auto-filled with each rule's default, not the role-correct value (about 120–150 of 281 rules would go red), and the declarative loop cannot prove isolation anyway. Cross-venue reads are named cases in `multi-venue.test.ts`. |
| R8 | `cafe_settings` | Untouched; it moves with `venue_settings` in slice 2 (six key-based accessors, a public view, two edge functions). |
| R9 | Cross-venue integrity | Composite foreign keys (`reservations(court_id, venue_id) → courts(id, venue_id)`, tabs → reservations, orders → tabs, guest_sessions → cafe_tables, station_staff and device_heartbeats → stations). No generic trigger: it would run as the writing role (the 0121 grant trap) and add lock-order surface. |
| R10 | Indexes | Four now (`audit_log`, `reservations`, `orders`, `payments` by `(venue_id, time)`); the rest in slice 3, when queries filter by venue. A leading column with one distinct value is never chosen today. |
| R12 | Functions re-issued | Exactly four: `heartbeat`, `set_station_staff`, `is_degraded()`, `venue_mode()`. The 41 RPCs that take `p_device_id` are untouched until slice 3. |
| R13 | Error codes | `VENUE_REQUIRED`, `STATION_UNKNOWN` mapped in the operator now; web and mobile cannot receive them before slice 3. |

## How a venue is resolved

`app.resolve_venue(p_station_id)` never raises; `app.current_venue()` raises `VENUE_REQUIRED`
when it returns null; `app.current_venue_or_default()` falls back to the default venue.

1. The station: the argument, else the transaction-local `app.station_id` set by a re-issued RPC
   (slice 1: `heartbeat` only) → the `stations` row → its venue.
2. `app.venue_id`, a transaction-local setting a definer body may assert (slice 3).
3. The caller's `staff_venues` rows: exactly one → that venue; more → undecidable.
4. Exactly one active venue → that venue.

Neither setting is reachable from a PostgREST client; only granted `app.*` functions can set
them, and `check:rpc-registry` replays every grant.

## Gaps this slice leaves on purpose

- A manager at venue A can still read an **active** court, rate rule or menu item at venue B
  through the guest (`is_active`) branch of the shared policies. Slice 4 closes it when the guest
  apps carry a venue.
- `open_day`'s `PREVIOUS_DAY_OPEN`, `close_day` and `business_date()` read `day_sessions` with no
  venue filter; two rows may now share a date. First item of slice 3's day-close family.
- `staff_breaks.station_id` has no foreign key to `stations` — a break row outlives its station.
- `retire_device` deletes the heartbeat row and leaves the registry row; "retire station" is
  slice 4's screen.
- `venues.name_en/timezone/phone` and `venue_settings.venue_name/timezone/phone` are two copies
  of three facts until slice 2 moves the writer.
- **`check:migrations` judges zero files on a direct push to `main`**: it diffs against
  `merge-base origin/main HEAD`, which is HEAD. Run it locally with `--base=<pre-slice sha>`; the
  three index files (0132, 0134, 0135) need `MIGRATION_RISK_ACCEPTED` there. Not this slice's job
  to change the gate; recorded so nobody trusts the green tick.
- Per-venue realtime topics would blind SEC-28 (`check-broadcast-payloads.mjs:125` matches the
  literal `'kds'`); the topic scheme and the gate change together in slice 4.
