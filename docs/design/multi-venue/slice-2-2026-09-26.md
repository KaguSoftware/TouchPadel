# Multi-venue, slice 2: settings per venue (2026-09-26)

> **Status 2026-09-26:** live on production. It was pushed with slices 3–4 (`b3431224`) and
> verified at 0227, 0 pending. There was no staging rehearsal. The rollout record is in
> `slice-3-4-2026-09-26.md` under "Rollout".

Milestone 1 of Phase 2. Slice 1 (0122–0139, `slice-1-2026-09-21.md`) laid the venue axis on 35
tables. Slice 2 makes the settings follow it: migrations **0207–0214**. As with slice 1, nothing
changes for users. There is still one venue on the client's project, every default still
resolves, and no app changes behaviour.

The plan for the whole milestone (slices 2–4 and the owner's "Open a new branch") was approved by
Parsa on 2026-09-26. Its decisions MV1–MV8 are restated where this slice uses them.

## What changed

| # | Migration | What it does |
|---|---|---|
| 0207 | `platform_settings` | A singleton for what belongs to the whole chain (MV5): currency, the chain's timezone for the LLM day, the per-guest hold cap, and every LLM budget and price-list key. Every LLM and assistant reader and writer is re-issued against it. The old `venue_settings` columns stay, unread, until a later drop, so an edge function still on the previous deploy keeps working. |
| 0208 | `venue_settings_per_venue` | The boolean PK is dropped and a unique index on `venue_id` replaces it. `id` stays (always true) so a body not yet re-issued still compiles. `venues` gains `address_en`, `address_ar` and `map_url`. `venue_settings_public` lists one row per active branch, with `venue_id`, slug, both names and the address. `set_opening_hours`, `set_waiter_call_cooldown` and `set_venue_details` take `p_venue_id` and write one branch. `set_venue_details` keeps `venues` in step and sends the hold cap to `platform_settings`. |
| 0209 | `cafe_settings_per_venue` | `venue_id` is added, keyed `(venue_id, key)`. The four accessors take an optional `p_venue`. Without it they resolve the caller's venue and fall back to the default branch, so every existing reader keeps working. The writers take the branch; the manager's featured-discount lock (#57) now compares against that branch. The public view appends `venue_id`, the staff policy gains the venue axis, and the realtime payload names the branch. |
| 0210 | `booking_settings_per_venue` | `price_slot`, `assert_bookable`, `assert_not_degraded_for` (+ `p_venue`), `hold_slot`, `confirm_booking`, `staff_create_reservation`, `cancel_reservation`, `series_occurrences` (+ `p_venue`), `preview_series` and `create_series` read their court's (or reservation's) branch. `hold_slot` also names the venue on the hold row: a guest has no station or membership, so with two open branches the column default could not resolve. |
| 0211 | `cafe_settings_readers_per_venue` | `venue_business_date` reads the start hour of its own branch. `business_date(timestamptz)` delegates to it at the caller's resolved venue. `open_table_session`, `touch_guest_session`, `raise_waiter_call`, `compute_tab_totals`, the two guest-order triggers and `add_order_items` read their table's, session's, order's or tab's branch. The new session row and the waiter-call row name that branch. |
| 0212 | `degraded_promotions_telegram_per_venue` | `is_degraded(uuid)` and `venue_mode(uuid)` drop the singleton fallback. **Promotions per branch (MV2):** `promotions.venue_id` is nullable, NULL meaning every branch. Existing promotions are backfilled to the default branch, because their scope names its ids. New rows take the writer's venue. The owner's `set_promotion_venue` makes one chain-wide, refused with `PROMOTION_SCOPE_BRANCH` when its scope names a court, category or item (a CHECK agrees). `eligible_promotions` offers a tab its branch's promotions plus the chain-wide ones. **Telegram per branch (MV3):** `enqueue_telegram` (+ `p_venue`) files each alert at its order's or call's branch with that branch's group. `telegram_send_test` (+ `p_venue_id`), `retry_telegram_outbox` and `telegram_apply_action` follow the branch. |
| 0214 | `analytics_stock_settings_per_venue` | The analytics helpers read the settings of the analysis branch, and only its courts: `analytics_bounds`, `analytics_open_cells`, `analytics_open_minutes`, `analytics_courts_summary`, `analytics_courts_endings` and `reports_available_minutes`. The analysis branch is `app.current_venue_or_default()`, resolved once per call. Before this, a bare `cross join venue_settings` counted every opening-hours cell once per branch. `v_expiring_soon` (which appends `venue_id`) and `flag_expired_batches` judge each batch against its own branch, and the cron's alert is filed at the batch's branch. |
| 0213 | `venue_id_not_null` | `SET NOT NULL` on 37 tables, each backed by slice 1's validated presence CHECK, so no row is scanned. `promotions` stays nullable by design. `types.gen.ts` now says `venue_id: string`. |

Edge functions in this slice:
- `assistant-chat`, `assistant-component`, `assistant-job` and `release-review` read the model,
  prices and timezone from `platform_settings`.
- `telegram-send` reads the language per row's branch and follows a group migration on that
  branch only.
- `telegram-callback` moves and stamps every branch whose group the chat is.
- `telegram-diagnose` takes an optional `venue_id` (default: the oldest active branch).
- `assistant-chat` reads the business-day start hour of the default branch until the assistant
  gets its branch scope (slice 4).

Tests and scripts:
- `tests/helpers.ts`: cafe-settings snapshot and restore key on `(venue_id, key)`, and the venue-B
  probe gets a copy of venue A's `venue_settings` row (what `create_branch` will do).
- `multi-venue.test.ts` lists `cafe_settings` as scoped and `platform_settings` as global.
- The two LLM tests set limits on `platform_settings`.
- `scripts/check-rpc-authz.mjs` reads the probe court's own branch timezone.
- `scripts/measure-assistant-tokens.mjs` reads `platform_settings`.

## Decisions taken while building

| # | Question | Call |
|---|---|---|
| S2-1 | Drop the old LLM columns from `venue_settings` now? | No. They stay one release (commented DEPRECATED) so an edge function on the previous deploy keeps working; a later migration drops them. |
| S2-2 | `venues` or `venue_settings` as the one copy of name, phone and timezone? | Both stay. `set_venue_details` is the only writer and keeps them in step. Moving every reader of `venue_settings.timezone` in this slice would re-issue dozens more bodies for no user-visible gain. |
| S2-3 | Readers that cannot know their branch (the zero-argument accessors) | They resolve the caller's venue (station, `app.venue_id`, only membership, only active venue) and fall back to the default branch. The protocol and staff-phone bodies already set `app.venue_id`, so they resolve right with no re-issue. |
| S2-4 | Analytics and reports | The helpers' settings reads were fixed here (0214): a second branch's settings row made them double-count or raise. The top-level report and analytics functions get `p_venue_id` ("All branches" for the owner) and venue filters in slice 3. They will set `app.venue_id`, which the helpers already resolve. `open_day` is slice 3's day family. |
| S2-5 | Promotions backfill | To the default branch, not "every branch". Their scope names that branch's court, category and item ids. |
| S2-6 | A PK on `venue_settings.venue_id` | Not added. A unique index plus NOT NULL gives the same guarantee without a validating `ADD CONSTRAINT`, which the gate refuses. |

## Waiver

`check:migrations` flags two non-concurrent unique indexes (0208 on the one-row `venue_settings`,
0209 on the ~25-row `cafe_settings`) and the 37 `SET NOT NULL` statements in 0213. Each of those is
backed by a validated CHECK, so no row is scanned. Waiver text for the push:
`MIGRATION-RISK-ACCEPTED: slice 2: unique indexes on 1-row venue_settings and ~25-row
cafe_settings; SET NOT NULL backed by validated CHECKs`.
