# Phone OTP (one-time code by SMS / WhatsApp) — the dormant base, design note 2026-09-05

For the security reviewer (SEC), the PR description, and whoever runs the activation later.
**Companion:** the client-facing runbook `docs/client/phone-otp-activation.md` (the "activate otp" checklist).
**Approved plan:** `~/.claude/plans/for-the-login-authentication-optimized-candy.md`.
**Precedent:** `docs/design/social-signin-2026-09-01.md` (the last vendor addition outside the SOW).

## 1. What and why

**Vendor addition scaffold, not contract work.** The signed SOW (`docs/scope/touch-padel-phase1-scope-of-work.txt`
L259-260) lists "Phone / SMS one-time-code login" as NOT INCLUDED, with the boxed rationale that per-message cost
and a regional SMS contract are the blockers — and that "phone-based identity can be added later without a data
migration, because the phone number is captured on the profile from day one". Security Layer v1.1 §5.2 *recommends*
phone + OTP; the contract was the only reason it was closed (`docs/security/security-general.md` D5 / SEC-22).

**What the owner asked for (2026-09-05).** Build everything that does not depend on their decisions, fully tested,
**dormant**, so that activation is configuration plus secrets plus one flag — "activate otp" — not a code change.

**Three independent switches, all shipped OFF.**

| # | Switch | Where | Off means |
|---|---|---|---|
| 1 | `EXPO_PUBLIC_PHONE_OTP=on` | `apps/mobile/eas.json` per profile / `.env` locally | No "Continue with phone" button, no Verify-phone row; a direct navigation to the two screens redirects away |
| 2 | Phone provider + Send SMS hook | Supabase dashboard → Auth (hosted) | GoTrue refuses `signInWithOtp({ phone })` outright |
| 3 | `app.sms_limits.enabled` | migration 0069, one row | The hook answers every send with `SMS_DISABLED`; nothing is ever billed |

Switch 3 is the safety net for switch 2: someone enabling the Phone provider early in the dashboard still spends
nothing. Locally the flow works **end to end with no vendor**: GoTrue's `test_otp` number (`0770 000 0001`, code
`123456`, `packages/db/supabase/config.toml`) accepts its fixed code and never invokes the hook.

**Owner decisions still open (D4a–D4d, section 7).** Provider and channel; extra method vs default; the desk-account
claim policy; whether the Iraq-only allow-list stays. None of them is needed to build; all of them are needed to
switch on.

## 3. Identity model — what each existing account kind does when phone login exists

GoTrue keys phone identity on `auth.users.phone` (E.164 digits, unique). `profiles.phone` is a free-text profile field:
not unique, not verified, dialled by the desk. They are DIFFERENT columns with different meanings and this design
keeps them so.

| Account kind today | `auth.users.phone` | On activation |
|---|---|---|
| **New phone sign-up** | set + confirmed by GoTrue | Trigger (0069) copies it to `profiles.phone`; name is `''`; verify-otp routes to complete-profile (name) before anything else. `confirm_booking`'s `PHONE_REQUIRED` (0059) passes. No password exists; change-password is hidden (`hasRealEmail`). |
| **Email / social user** who typed a phone at sign-up | NULL | A phone sign-in with that number would mint a SECOND account. The Profile tab offers **Verify phone number** (`startPhoneLink` → `verifyPhoneLink`, type `phone_change`), which sets `auth.users.phone` on the SAME user and rewrites `profiles.phone` to the number that proved itself. **No blind backfill** from `profiles.phone`: a mistyped profile phone would hand the account to whoever owns that number. |
| **Desk-created walk-in** (`<digits>@guest.touch.local`, phone typed by staff) | NULL | This is the "future phone-based claim flow" the desk function's header promised. Setting `auth.users.phone` (unconfirmed) lets the guest's first OTP sign-in land on their existing account with their bookings. Residual risk: a staff typo hands account A's history to number B's owner. **Owner decision D4c** — shipped as a documented, gated SQL script in the runbook, not a migration. |

Pre-activation audit (runbook): canonical-phone duplicates across `profiles` (there is no unique index), and how
many `profiles.phone` values fail `toE164Iraq`.

## 4. Abuse and cost controls

Every OTP is a paid message (OTPIQ quotes 80 IQD/SMS for the first 250 a month, then 100 IQD Asiacell/Korek and
250 IQD Zain; WhatsApp cheaper). "SMS pumping" — bots requesting codes to premium-rate ranges — is the standard
attack on any OTP endpoint. Layers, outermost first:

1. **GoTrue** — `sms_sent` per hour project-wide (30 locally; set on hosted), `sign_in_sign_ups` per IP per 5 min
   (GoTrue default), `max_frequency` 60 s per phone, `token_verifications` on wrong-code guesses, OTP expiry
   (dashboard; keep ≤ 5 min). The hook never sees the client IP — GoTrue calls it, not the phone — so per-IP stays here.
2. **The hook's gate** (`app.sms_send_gate`) — `enabled` kill switch (default false), `allowed_prefixes` (`{964}`:
   the single most effective pumping control for a local venue), `per_phone_per_day` (5) on the canonical number so
   three spellings of one phone are one budget, `daily_total` (500) as the project ceiling. Refusals are logged with
   their reason. The limits row is `SELECT … FOR UPDATE`d so two concurrent calls cannot both read "4 of 5".
3. **The send log** (`app.sms_sends`) — one row per attempt with vendor id and cost: the activation-day watch and
   the invoice reconciliation.
4. **The mobile gate** — `toE164Iraq` refuses anything that is not an Iraqi mobile before a request leaves the phone.

Not in the first cut: CAPTCHA (Turnstile / hCaptcha) on the OTP endpoints — GoTrue supports it, React Native makes
it awkward; it is the next escalation if the log shows pumping despite the allow-list.

## 5. Security checklist (SEC reviewer)

- [x] Hook authenticity: Standard Webhooks HMAC-SHA256 over `id.timestamp.rawBody`, secret from
      `SEND_SMS_HOOK_SECRET` (`v1,whsec_…`), constant-time compare, ±300 s tolerance, **fail closed** on an unset or
      malformed secret (`verify.ts`, tested).
- [x] `verify_jwt = false` is deliberate and documented in `config.toml`; nothing else in the function trusts headers.
- [x] No client role can call `sms_send_gate` / `sms_send_result` (revoked from `public, anon, authenticated`;
      `service_role` only). `check-rpc-authz.mjs` therefore never sees them; the db test asserts refusal for anon and
      a staff session.
- [x] The kill switch defaults OFF and is checked before anything is billed; an early dashboard flip spends nothing.
- [x] The code is never logged on hosted (`_shared/sms/log.ts` redacts unless running under `functions serve`; tested).
- [x] Exactly one file per vendor knows its hostname and secrets, and the hook names none of them (`sendSms` is the
      only door; boundary test in `sms-provider.test.ts`).
- [x] Phone accounts have no password; change-password is hidden for them and for desk-created synthetic accounts.
- [x] No blind backfill of `auth.users.phone` for email/social users (account-takeover vector); linking requires a
      code to the number.
- [x] The template stays in one UCS-2 segment (≤70 UTF-16 units, tested) — cost, not security, but it is what an
      attacker doubles.
- [ ] At activation: hosted rate limits set (`sms_sent`, OTP expiry ≤ 5 min), `allowed_prefixes` confirmed,
      `test_otp` review number added, first-day watch on `app.sms_sends` (runbook §C).
- [ ] At activation: SEC-22 reopened only with the owner's written decision D4a–D4d; the D5 row in
      `security-general.md` updated.

## 6. Error handling contract (what the guest sees)

| Source | Signal | Copy |
|---|---|---|
| Not an Iraqi mobile | `validatePhoneInput` → `PHONE_INVALID` | `auth.phoneInvalid` |
| Wrong or stale code | GoTrue `otp_expired` (one code for both) | `auth.otpInvalid` |
| GoTrue send limits | `over_sms_send_rate_limit`, `over_request_rate_limit` | `auth.otpTooMany` |
| Hook refused: kill switch / unauthorized | message `SMS_DISABLED` / `UNAUTHORIZED` | `auth.phoneSignInUnavailable` |
| Hook refused: prefix | `PHONE_NOT_ALLOWED` | `auth.phoneInvalid` |
| Hook refused: caps | `PHONE_RATE` / `DAILY_CAP` | `auth.otpTooMany` / `auth.otpSendFailed` |
| Vendor failure | `SMS_SEND_FAILED`, `sms_send_failed` | `auth.otpSendFailed` |
| Provider off / hook down | `phone_provider_disabled`, `otp_disabled`, `hook_*` | `auth.phoneSignInUnavailable` |
| Offline | `isTransportError` | `errors.network` |

## 7. Open owner decisions (needed to activate, not to build)

- **D4a — provider and channel. DECIDED 2026-09-12: OTPIQ, SMS only (no WhatsApp; `OTPIQ_PROVIDER=sms`).** Local aggregator with WhatsApp-first + SMS fallback (recommended for Iraq
  deliverability and cost; OTPIQ is one) vs Twilio Verify. The contract, the alphanumeric sender-id registration
  with Asiacell (required since 2026-07-01; Zain/Korek drop numeric senders) and any WhatsApp Business verification
  (Meta business verification: one to two weeks) are on Touch's side and are the schedule long pole.
- **D4b — scope. DECIDED 2026-09-12: the default method.** Phone is the CTA on Welcome, Sign in and Create account;
  email + social are the alternatives. Button order and prominence only; no flow changed. The owner also asked about
  an SMS→email delivery fallback and chose this instead: it needs an email vendor the functions do not have, and it
  cannot help a new phone sign-up (no email known) — "resend" plus a registered sender id is the fallback.
- **D4c — desk-account claim.** Backfill `auth.users.phone` for `@guest.touch.local` accounts (accept the staff-typo
  risk) or have staff correct numbers first. Runbook §D carries the gated script.
- **D4d — Iraq-only.** Keep `allowed_prefixes = {964}` (recommended) or add codes. A single `update`.

## 8. What is NOT covered by this note

- Android SMS auto-read (needs the SMS Retriever app hash in the message, which breaks the one-segment budget).
- CAPTCHA on the OTP endpoints (section 4).
- An owner-facing screen for `app.sms_limits` / `app.sms_sends` (SQL for now).
- Account deletion for phone-only accounts (joins the SEC-15/16 dependency the social note recorded).
- The OTPIQ adapter's request shape against a live account — it is written from public client libraries and
  must be re-verified at activation (§C of the runbook says how).
- Anything on the operator desktop or the web app; this is mobile-only by the owner's request.
